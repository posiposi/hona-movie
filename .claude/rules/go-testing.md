# Go Testing Rules

## Testing Scope

テストは**プロジェクト固有のロジック・振る舞いのみ**を検証対象とする。ライブラリの挙動確認や、起動・配線のみで固有ロジックを持たないコードにはテストを書かない。

### Write tests for (テストを書く対象)

- ドメインモデルのビジネスロジック（値オブジェクト、エンティティ、ドメインサービス）
- アプリケーションサービスの振る舞い（ユースケース層の制御フロー）
- 自前の分岐・変換・判定ロジック
- 自前のハンドラ・ルーティング・レスポンス仕様
- 実DB に対する統合的な振る舞い（リポジトリ実装の検証）

### Do NOT write tests for (テストを書かない対象)

- ライブラリや言語機能そのものの挙動確認
- ライブラリのラッパー関数でライブラリ出力を検証するだけのもの
- env 読込ライブラリのマッピング動作確認
- `//go:embed` でファイルが埋め込まれることの確認
- 外部ライブラリが接続失敗時にエラーを返すことだけの確認
- マイグレーション等のデータ投入のみの処理
- Seeder（マスターデータ投入・初期ユーザー作成等）— ビジネスロジックを含まないデータ投入処理のためテスト不要
- sqlc 等のコード生成ツールが生成したコードそのもの
- エントリーポイント（`cmd/*/main.go`）— 起動・配線処理のみでプロジェクト固有のロジックを含まないためテスト不要

### Decision Criteria (判断基準)

「そのテストが落ちるのは自分たちのコードに不具合があるときか、それともライブラリ側の仕様が変わったときか」— 後者のみを検出するテストは不要。

## Testing Style

- `t.Error` を優先し、可能な限りテストを続行させる。`t.Fatal` はセットアップ失敗時のみ
- 失敗メッセージ形式: `YourFunc(%v) = %v, want %v`
- assertion ライブラリは使わない。標準比較 + `go-cmp` を使用
- 構造体比較は deep equality で行い、手動フィールド比較を避ける
- テストヘルパーではエラーを返し、fail 判断はテスト関数自身に委ねる
- Table-driven tests を活用し、テストケースの追加を容易にする

## Test File Naming

- テストファイル名: `{対象ファイル名}_test.go`（Go標準に従う）
- ファイル名に `integration` は含めない。integrationテストは `//go:build integration` タグで区別する
- 配置: テスト対象と同じディレクトリに配置する

| テスト種別 | ビルドタグ | 実行コマンド |
|-----------|-----------|------------|
| Unit test | なし | `go test ./...` |
| Integration test | `//go:build integration` | `go test -tags=integration ./...` |
