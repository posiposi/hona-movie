# コードレビュースキル

## レビューフロー

レビューは以下の2つの観点で実施する。

### 1. 一般的なコード品質の確認

変更差分（`git diff`）を確認し、以下の一般的な品質観点をレビューする。

- 不要コード・重複・過度な複雑度
- セキュリティ脆弱性（OWASP Top 10）・機密情報の混入
- 入力バリデーションの不足
- テストカバレッジの不足
- バグ（ロジックエラー、nil参照等）

### 2. プロジェクト固有観点のレビュー

本プロジェクト固有の規約・設計パターンを確認する。

#### 1. DDD層の責務分離

- ドメイン層が外部パッケージ（HTTP、DB等）に依存していないか
- アプリケーション層がHTTP固有の概念（リクエスト/レスポンス）を扱っていないか
- インターフェース層（ハンドラ）にビジネスロジックが含まれていないか
- インフラ層がドメイン層のPortインターフェースを正しく実装しているか

#### 2. 依存関係の方向

- 依存性逆転の原則が守られているか（ドメイン層 ← 他の層）
- 集約間の参照がIDのみで行われているか

#### 3. CQRSパターン

- Command PortとQuery Portが分離されているか
- Query操作が副作用を持っていないか

#### 4. DDD命名規則

- Go命名規則（MixedCaps）に準拠しているか
- ファイル名がsnake_caseで適切な命名か
- ドメインオブジェクトの不変性が守られているか

#### 5. ファクトリ関数

- エクスポートされたコンストラクタ関数（`New*`）が提供されているか
- ファクトリ関数内でバリデーションが行われているか

#### 6. テスト規約

- テスト名が期待する振る舞いを日本語で記述しているか
- テストファイルが規約通りの場所に配置されているか（`*_test.go`）
- 冗長なテストケースや、言語・ライブラリ機能自体をテストしているケースがないか

## レビュー結果の分類

### 重大（修正必須）

- セキュリティ脆弱性・機密情報の混入
- バグ（ロジックエラー、nil参照等）
- DDD層の責務違反
- 依存関係の方向の誤り

### 改善推奨

- 不要コード・重複・過度な複雑度
- DDD命名規則の改善余地
- テスト規約との乖離

### 良い点

- 適切なDDD設計
- 読みやすいコード
- 適切なテストカバレッジ
